---

## 1. Background & Goal

- **Problem Statement**：既有的 host 形態已經能看到使用者這台機器上真正在用的排程，但每次都得開終端機下指令、再開瀏覽器分頁。使用者要的是「隨時在那裡、不用特地去開」——尤其是排程失敗時，希望是它來找我，而不是我去翻。
- **Expected Outcome**：使用者不必開終端機、不必開瀏覽器分頁，就能在選單列瞄一眼知道「現在有沒有事要理」；納管排程失敗時會主動被告知；點開後能做的事與既有介面完全一致。
- **Out of Scope**：
  - macOS 以外的平台。
  - 由本應用負責排程（排程始終由系統的排程機制負責）。
  - 在應用內切換要看哪一份排程表。
  - 讓其他裝置連進來檢視。
  - 應用關著期間發生的失敗的補報通知。
  - 開機自動啟動。

---

## 2. User Personas

- **Primary Role**：這台 Mac 的擁有者，同時是所有排程的作者與唯一使用者。
- **Usage Context**：日常在自己的 macOS 桌面上工作，排程在背景由系統跑。使用者大部分時間不看這個應用，只在（a）想確認某個排程有沒有跑、（b）被通知某個排程失敗、（c）要新增或修改排程時才互動。

## 3. User Stories & Acceptance Criteria

### US-01 — 選單列圖示反映「現在有沒有事要理」 [P0]

**作為** 這台機器的擁有者，**我要** 不點任何東西就能從選單列圖示知道排程有沒有出事，**以便** 不必為了確認一切正常而特地打開任何介面。

```gherkin
Scenario: 全部納管排程最近一次都成功
  Given 有三個納管排程,最近一次執行都成功
  When 使用者看選單列圖示
  Then 圖示呈現「正常」狀態

Scenario: 有納管排程最近一次失敗
  Given 有一個納管排程最近一次執行失敗
  When 使用者看選單列圖示
  Then 圖示呈現「有事要理」狀態

Scenario: 只有未納管的排程
  Given 排程表裡只有未納管的排程,它們的執行結果無從得知
  When 使用者看選單列圖示
  Then 圖示呈現「正常」狀態
  And 不因「無從得知」而標示為有事要理

Scenario: 納管排程從未執行過
  Given 有一個納管排程,沒有任何執行紀錄
  When 使用者看選單列圖示
  Then 圖示呈現「正常」狀態

Scenario: 讀不到使用者的排程表
  Given 這台機器上取得排程表的動作失敗
  When 使用者看選單列圖示
  Then 圖示呈現「無法取得」狀態
  And 這個狀態與「正常」在外觀上明確可分

Scenario: 先前失敗的排程最新一次成功了
  Given 有一個納管排程,前一次執行失敗,最新一次執行成功
  When 使用者看選單列圖示
  Then 圖示呈現「正常」狀態
  And 不因歷史上曾經失敗而持續標示為有事要理

Scenario: 納管排程因為跑太久被中止
  Given 有一個納管排程,最近一次執行因逾時被中止
  When 使用者看選單列圖示
  Then 圖示呈現「有事要理」狀態
```

### US-02 — 選單列展開的是摘要，不是全貌 [P0]

**作為** 這台機器的擁有者，**我要** 點一下選單列就看到每個排程的名稱、下次執行與最近結果，**以便** 在三秒內決定要不要深入看。

```gherkin
Scenario: 三種結果並存的摘要
  Given 有三個排程:一個納管且最近一次成功、一個納管且最近一次失敗、一個未納管
  When 使用者點開選單列
  Then 三筆都列出,各自顯示名稱、下次執行時間與最近結果
  And 最近結果分別標示為「成功」、「失敗」與「無從得知」

Scenario: 未納管且輸出無處可讀的排程
  Given 有一個未納管的排程,其指令沒有把輸出導向任何地方
  When 使用者點開選單列
  Then 該筆的最近結果標示為「無從得知」
  And 不顯示為空白,也不顯示為成功

Scenario: 排程表是空的
  Given 排程表裡一個排程都沒有
  When 使用者點開選單列
  Then 顯示「目前沒有排程」

Scenario: 沒有下次執行時間的排程
  Given 有一個排程只在開機時執行,不存在可預測的下次執行時間
  When 使用者點開選單列
  Then 該筆的下次執行欄標示為「不適用」
  And 不留空白,也不顯示任何推測出來的時間

Scenario: 已停用的排程
  Given 有一個已被停用的排程
  When 使用者點開選單列
  Then 該筆標示為「已停用」
  And 其下次執行欄標示為「不適用」

Scenario: 從摘要進入詳情
  Given 選單列摘要中列出了某個排程
  When 使用者點選該筆
  Then 開啟完整視窗,並停在該排程的詳情

Scenario: 讀不到排程表時的摘要
  Given 這台機器上取得排程表的動作失敗
  When 使用者點開選單列
  Then 顯示取得失敗的說明
  And 不顯示任何一筆排程,也不顯示「目前沒有排程」
```

### US-03 — 通知只在「應用開著的期間、納管排程失敗」時出現 [P0]

**作為** 這台機器的擁有者，**我要** 排程失敗時被主動告知，**以便** 不必定期巡邏就能發現問題；同時我不要被成功訊息或無從判斷的事件打擾。

```gherkin
Scenario: 納管排程失敗時通知
  Given 應用正在執行
  And 有一個納管排程執行失敗
  When 該次執行結束
  Then 跳出一則系統通知,指出是哪個排程失敗
  And 圖示同步呈現「有事要理」狀態

Scenario: 成功不通知
  Given 應用正在執行
  And 有一個納管排程執行成功
  When 該次執行結束
  Then 不跳出任何通知

Scenario: 未納管排程不通知
  Given 應用正在執行
  And 有一個未納管的排程剛執行完畢
  When 該次執行結束
  Then 不跳出任何通知

Scenario: 逾時中止的通知與失敗有別
  Given 應用正在執行
  And 有一個納管排程因為跑太久被中止
  When 中止發生
  Then 跳出一則系統通知,說明該排程是因逾時被中止
  And 通知內容與「執行失敗」可以區分

Scenario: 離線期間的失敗不補通知
  Given 應用未執行的期間,有兩個納管排程失敗
  When 使用者開啟應用
  Then 不跳出任何通知
  And 圖示呈現「有事要理」狀態

Scenario: 連續失敗各通知一次
  Given 應用正在執行
  And 同一個納管排程在期間內連續失敗兩次
  When 第二次執行結束
  Then 總共跳出兩則通知,每次失敗各一則

Scenario: 同一次失敗不重複通知
  Given 應用正在執行
  And 有一個納管排程失敗並已跳出通知
  When 應用再次確認執行狀況而該排程沒有新的執行
  Then 不再為同一次失敗跳出通知
```

### US-04 — 完整視窗的能力不打折 [P0]

**作為** 這台機器的擁有者，**我要** 桌面形態能做的事與既有介面完全一致，**以便** 不必為了改一個排程而切回另一種啟動方式。

```gherkin
Scenario: 操作能力與既有介面一致
  Given 完整視窗已開啟
  When 使用者檢視排程詳情、新增、編輯、停用、手動觸發一次或將排程轉為納管
  Then 每一項都可以完成
  And 沒有任何一項在桌面形態被移除

Scenario: 輸出無處可讀時說明原因
  Given 有一個未納管的排程,其輸出無處可讀
  When 使用者在完整視窗中檢視它的輸出
  Then 顯示「無輸出可讀」的說明與「轉為納管」的建議動作
  And 不顯示一片空白

Scenario: 同一個排程不重複手動觸發
  Given 有一個排程正在手動執行中
  When 使用者再次按下手動觸發
  Then 動作被拒絕,並說明該排程正在執行中

Scenario: 排程表被外部改動時拒絕覆寫
  Given 使用者在別處改動了排程表
  When 使用者在完整視窗中送出一項變更
  Then 變更被中止,並說明排程表已被外部改動
  And 使用者在別處的改動未被覆蓋

Scenario: 完整視窗已開啟時再次開啟
  Given 完整視窗已經開著
  When 使用者再次從選單列選擇開啟完整視窗
  Then 將既有的視窗帶到最前
  And 不另外開出第二個視窗
```

### US-05 — 只看本機真正那份排程表，且完全自用 [P0]

**作為** 這台機器的擁有者，**我要** 桌面形態看到的就是我真正在用的排程，且只有我這台機器看得到，**以便** 不必擔心看錯來源，也不必擔心多開一個對外的入口。

```gherkin
Scenario: 看到的是本機真正在用的排程
  Given 使用者這台機器上真正在用的排程表有三個排程
  When 使用者開啟應用
  Then 看到的就是那三個排程

Scenario: 與容器形態互不影響
  Given 同一台機器上另有容器形態在執行
  When 使用者開啟應用
  Then 只看到本機真正在用的排程
  And 應用內不提供切換來源的選項

Scenario: 其他裝置連不進來
  Given 應用正在執行
  When 另一台電腦或手機嘗試連入檢視
  Then 連線不成立

Scenario: 已有另一個桌面應用在執行
  Given 這台機器上已經有一個本應用在執行
  When 使用者再啟動一次
  Then 不重複進駐選單列
  And 提示已經有一個在執行中
```

### US-06 — 應用不是排程器 [P1]

**作為** 這台機器的擁有者，**我要** 清楚知道關掉這個應用不會影響任何排程，**以便** 放心地隨時關掉它。

```gherkin
Scenario: 應用沒開,排程照跑
  Given 應用完全沒有執行
  And 排程表裡有一個排在凌晨三點的排程
  When 時間到達凌晨三點
  Then 該排程照常執行

Scenario: 結束應用不影響排程
  Given 應用正在執行
  When 使用者結束應用
  Then 所有排程照常執行,執行紀錄照常累積

Scenario: 應用關著期間未納管排程跑完
  Given 有一個未納管的排程在應用關著時執行完畢
  When 使用者之後開啟應用
  Then 仍然只能看到它輸出到的檔案內容
  And 它的最近結果仍為「無從得知」
```

## 4. Business Flow & Logic

### 主流程

```
使用者啟動桌面應用
  → 進駐選單列，圖示先呈現「正常」
  → 立刻取得一次排程摘要，圖示依結果更新
  → 進入定期確認循環（見下方「資料新鮮度」）
      ├─ 取得成功 → 更新摘要與圖示
      │              → 比對「本次新完成的納管執行」→ 失敗者各發一則通知
      └─ 取得失敗 → 圖示轉為「無法取得」，摘要顯示失敗說明，不發通知

使用者點選單列某一筆／「開啟完整視窗」
  → 若視窗已開 → 帶到最前
  → 否則開啟完整視窗（內容即既有介面），必要時停在指定排程

使用者結束應用
  → 退出選單列；排程與執行紀錄完全不受影響
```

### 核心業務規則

| # | 規則 |
|:--|:---|
| BR-1 | **整體狀態只有三種**：`正常`／`有事要理`／`無法取得`。取得排程表失敗一律為 `無法取得`；否則只要存在任一個「納管且最近一次執行為失敗或逾時中止」的排程即為 `有事要理`；其餘一律 `正常`。 |
| BR-2 | **「無從得知」不等於失敗。** 未納管排程無論如何都不影響整體狀態，也不觸發通知。 |
| BR-3 | **只看最近一次。** 整體狀態只取每個納管排程的最近一次執行結果，不累積歷史失敗。 |
| BR-4 | **最近結果只有四種呈現**：`成功`／`失敗`／`執行中`／`無從得知`。逾時中止歸入 `失敗` 呈現，但通知文字須指出是逾時。 |
| BR-5 | **通知的觸發條件**：該次執行為納管排程、已結束、結果為失敗或逾時中止，且是本次確認才新出現的（應用開始執行之前就已存在的執行紀錄一律不通知）。 |
| BR-6 | **通知不重複。** 同一次執行只通知一次；同一個排程的不同次執行各自通知。 |
| BR-7 | **下次執行時間不猜。** 已停用或不存在可預測下次執行時間的排程，一律標示「不適用」。 |
| BR-8 | **來源固定。** 桌面形態一律看使用者這台機器上真正在用的那份排程表，不提供切換。 |
| BR-9 | **只限本機。** 完整視窗的內容只在這台機器內可取得，其他裝置無法連入。 |
| BR-10 | **單一實例。** 同一台機器同時只有一個桌面應用進駐選單列。 |

### 資料新鮮度

- 應用啟動時立即取得一次，之後**每 30 秒**重新確認一次。
- 30 秒是「通知即時性」與「不必要的重複讀取」之間的取捨：排程失敗的處理通常不是秒級任務，但超過一分鐘就會讓使用者覺得通知遲鈍。
- 使用者點開選單列時**不強制重新取得**——顯示的是最近一次確認的結果，避免點開的瞬間卡住。

### 邊界與失敗情況

| 情況 | 行為 |
|:---|:---|
| 取得排程表失敗（暫時性） | 圖示轉「無法取得」，摘要顯示原因；下次確認成功即自動恢復，不需要使用者重啟 |
| 取得排程表失敗期間 | **不發通知**——讀不到資料時無從判斷有沒有新的失敗，發通知等於瞎猜 |
| 排程數量很多 | 摘要最多列 **20 筆**，依下次執行時間由近到遠排序；有事要理的排在最前；被截斷時明確標示「另有 N 筆，請開啟完整視窗」 |
| 使用者在應用執行期間於別處改了排程表 | 下次確認時自然反映新的內容，不需要重啟 |
| 結束應用時仍有手動執行進行中 | **讓它跑完**——中止一個使用者主動要求的執行，比讓它在背景完成更糟 |
| 完整視窗被使用者關閉 | 應用繼續進駐選單列；下次可再開啟 |

## 5. UI/UX Design & Interaction

**選單列摘要（點開後）**

```
◷                               ← 選單列圖示（時鐘＋循環箭頭，template 圖示）
                                  有事時圖示旁補一個字元：`!` 有事要理／`?` 無法取得
┌──────────────────────────────┐
│ backup.sh        03:00   ✓  │  ← 名稱、下次執行、最近結果
│ sync-photos      每小時   ✗  │
│ cleanup          不適用   —  │  ← 「—」＝無從得知
│ old-report       已停用   —  │
├──────────────────────────────┤
│ 另有 3 筆…                    │  ← 超過 20 筆時才出現
│ 開啟完整視窗…                 │
│ 結束 cronwatch                │
└──────────────────────────────┘
```

- **圖示三態**：正常／有事要理／無法取得，外觀必須明確可分（不能只靠顏色深淺）。做法是**單一圖示 ＋ 有事時才出現的字元**：正常時只有圖示（絕大多數的時候，乾淨），`!` 表示有事要理、`?` 表示無法取得。圖示本身是 template 圖示，由 macOS 依淺色／深色選單列自行上色。
- **空狀態**：排程表為空時，摘要區顯示「目前沒有排程」，仍保留「開啟完整視窗」與「結束」。
- **失敗狀態**：取得失敗時，摘要區顯示失敗原因一行，不列出任何排程。
- **完整視窗**：內容即既有介面，不另做一套。點某一筆進入時直接停在該排程的詳情。
- **通知內容**：需包含排程名稱與失敗性質（執行失敗／逾時中止），讓使用者不必打開就知道是哪一個出事。

## 6. Non-Functional Requirements

- **效能**：**選單列在任何情況下都不得因為讀取而卡住。** 確認現況一律在背景進行，選單展開時顯示的是最近一次確認的結果。因此一次慢讀的後果是「畫面舊了幾秒」，而不是選單無法展開，也不是被誤標成取得失敗。
  > 本條於 `v1.0` 原訂為「須在 2 秒內完成，超過即視同取得失敗」。實作階段改以上述方式滿足其**意圖**：既有的資料讀取介面沒有可取消的機制，硬加逾時只能靠一條會洩漏的背景工作換一個假的保證，而把一次慢讀謊報成「讀不到」反而製造了一個不存在的問題。理由詳見 `ARCH.md` §8。
- **安全**：完整視窗的內容只在這台機器內可取得。本服務可執行任意指令，等同遠端 shell——桌面形態不得因為方便而放寬這一點。
- **相容性**：僅 macOS。其他平台上啟動桌面形態時，須給出明確的「此平台不支援」訊息，而不是失敗得不明不白。
- **可觀測性**：本專案無分析追蹤需求。

## 7. Dependencies & Risks

| 項目 | 說明 |
|:---|:---|
| 依賴 | 既有的 host 形態能力（取得使用者真正在用的排程表、執行紀錄、輸出）——桌面形態不引入任何新的資料來源 |
| 依賴 | macOS 的選單列與系統通知機制 |
| 風險 | 通知只對「常駐開著」的使用方式有效。若使用者想開才開，通知大部分時間等於不存在——圖示的狀態標記是對此的補償，它反映「目前」的事實，不受應用開關影響 |
| 風險 | 未納管排程在摘要中會呈現一排「無從得知」，直到使用者逐一納管。這是實話，優於編造一個結果 |
| 已接受的限制 | 應用不是排程器，關掉它不影響任何排程；反之，開著它也不會讓排程更準時 |
